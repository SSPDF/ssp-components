# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`@ssplib/react-components` is a published React component library (MUI 9 + React 19 since `1.0.0`) for SSP-DF internal projects. It ships form controls, auth providers, a Leaflet map, tables, modals and navbars. There is **no host application** here — components are developed and previewed exclusively through **Storybook**, and consumed by downstream Next.js apps. The library declares `react ^19`, `next ^16`, MUI `^9` / x-date-pickers `^9`, Emotion, `react-hook-form`, `dayjs` and `react-toastify` `^11` as `peerDependencies` — only the current major of each (policy of 27/09/2026) (see `lib-package.json`). UI copy and code comments are in Portuguese (pt-BR).

## Commands

```bash
npm run storybook        # dev environment — Storybook on :6006 (primary way to run/preview components)
npm run build            # production build via tsdown -> dist/ (one file per module: ESM .mjs + CJS .cjs + .d.mts/.d.cts). Needs Node ≥ 22.18 (the full dev suite needs ≥ 22.22.2 or ≥ 24.15, jsdom 30's floor — see `engines`). Runs prebuild (sync-version) first.
npm run dev              # tsc --watch (type-check only; noEmit is on in tsconfig)
npm run api              # json-server mock API on :7171, serving api-test.json (for Fetch* components in stories)
npm run build-storybook  # static Storybook -> storybook-static/
npm run pack:local       # build + pack dist/ into pack/*.tgz exactly as publish would — install that tarball in a consumer app to test (CI also uploads it as a run artifact, `ssplib-react-components-<version>-<head sha>`, on every PR)
```

Storybook stories are the main verification surface — when you change a component, update/add its `*.stories.tsx` and check it renders; the full check suite (typecheck, lint, vitest, visual snapshots, package checks, smoke app) is under **Verification** below. Formatting is Prettier (`.prettierrc`): 4-space tabs, single quotes, **no semicolons**, `printWidth: 200`, JSX single quotes. Match this exactly.

## Architecture

### Two parallel form systems — this is the most important thing to understand

The library has **two incompatible form-context mechanisms**, and components are split between them. Pick the right provider/decorator for the component you touch:

1. **Custom `FormContext`** (`src/context/form.ts`) — provided by `FormProvider` (`src/components/providers/FormProvider.tsx`). It wraps `react-hook-form` but **re-exposes methods under renamed keys**: `formRegister`, `formWatch`, `formSetValue`, `formReset`, `formControl`, `formHandleSubmit`, etc., plus `setFilesUid`/`submiting`. Components consume it via `useContext(FormContext)`. Used by the non-prefixed components: `Input`, `Table`, `CheckBox`, file uploads, etc. `FormProvider` also renders the `<form>` and shows a toast on invalid submit. Its `onSubmit` receives `(data, filesUid)`.

2. **Native react-hook-form context** — provided by `GenericFormProvider` (`src/components/providers/GenericFormProvider.tsx`), which is just RHF's `FormProvider` + `useForm`. Components consume it via the standard `useFormContext()` from `react-hook-form`. Used by the **`Generic*`-prefixed** components: `GenericInput`, `GenericTable`, `GenericFetchAutoComplete`, `GenericMaskInput`, `GenericMultInput`, `GenericDatePicker`. Its `onSubmit` receives `(data)` only.

When adding a story, mirror this split with the matching decorator: `src/decorators/FormBaseDecorator.tsx` (custom context) vs `src/decorators/GenericFormBaseDecorator.tsx` (RHF context). Both wrap the story in `SspComponentsProvider` + a submit button that dumps form data.

### Masked inputs and validation

Field types (`cpf`, `cnpj`, `cpf_cnpj`, `phone`, `cep`, `sei`, `rg`, `email`, `number`) drive both an IMask mask and a length/format validator, declared as lookup tables (`MASK_CONFIGS`, `VALIDATIONS`) inside the Input components and rendered through `MaskInput`/`GenericMaskInput` (`react-imask`). The newer `src/components/form/input/Input.tsx` is the more complete implementation (dynamic phone/cpf_cnpj masks via IMask `dispatch`, full `TextFieldProps` passthrough); follow its patterns over the older sibling components.

### Auth providers

Two providers both feed the shared `AuthContext` (`src/context/auth.ts`) with the `AuthReturnData` shape (`src/types/auth.ts`): `user`, `isAuth`, `userLoaded`, `login`, `logout`, `hasRole`/`hasAnyRole`/`hasAllRoles`, `accessToken`, etc.

- `KeycloakAuthProvider` — AD/Keycloak (`type: 'ad'`), auto token refresh, SSO init.
- `OAuthProvider` — gov.br OIDC (`type: 'govbr'`). Includes a **localhost/test bypass**: on `localhost` (or a configurable `testIP`) it skips the real OIDC flow and logs in with a provided `testToken`.

Only `OAuthProvider` writes the JWT to the `nextauth.token` cookie (`cookieName`, also exported as `AUTH_COOKIE_NAME`), via the internal helper `src/components/utils/cookies.ts` (byte-compatible with the `cookies-next@4` it replaced — don't change the encoding, or existing sessions stop being read). `KeycloakAuthProvider` declares the same `cookieName` but never writes it; its token lives in `keycloak-js`. Both keep the user avatar in `localStorage`.

### Public API & build

`src/index.ts` is the single barrel — **every public component and type must be exported here** or it won't ship. The build is `tsdown` (`tsdown.config.mts`, `unbundle` mode — only what `src/index.ts` and `src/types/{auth,form}.ts` reach is emitted, so stories/decorators/tests stay out without an exclude list); note root `tsconfig.json` has `strict: false`, so type errors do not block the build — be careful, the compiler will not catch much for you.

`SspComponentsProvider` is the top-level app wrapper consumers mount once: it renders the modal portal (`CustomModalProvider` from `src/components/modal/Modal.tsx`, exported as `MODAL`) and the react-toastify `ToastContainer`.

### Versioning & publishing

Version lives in **`lib-package.json`** (the package.json that actually gets published — copied to `dist/package.json`), not the root `package.json`. The `prebuild` hook runs `sync-version.cjs`, which copies `lib-package.json`'s version into the root `package.json`. **To release: bump the version in `lib-package.json`, then push a matching `v*` tag** (e.g. `v0.1.1`). `.github/workflows/publish.yaml` runs on that tag (or a manual `workflow_dispatch`), verifies the tag matches `lib-package.json`, refuses a version already on npm, builds, copies `lib-package.json`→`dist/package.json` and `README.md`/`CHANGELOG.md`→`dist/`, then `npm publish`es from `dist/` under the right dist-tag (a pre-release version goes to `next`, never `latest`). **It authenticates through npm trusted publishing (OIDC), not a token** (since 30/09/2026, after the old `NPM_TOKEN` expired and blocked `1.0.0-rc.4`): the package's npm settings trust `SSPDF/ssp-components` + `publish.yaml` with only "Allow npm publish", and the workflow has `id-token: write`. Don't add a token back; renaming the workflow file breaks publishing until the trusted publisher is recreated on npmjs.com. **Pushing to `main` no longer publishes** — that changed in Etapa 0 of the upgrade plan. **Semver since `0.1.0`** (the `0.0.x` line shipped everything, breaking changes included, as patches): while in `0.x`, a breaking change bumps the minor. Every release gets an entry in `CHANGELOG.md`. Release commits are `vX.Y.Z - <description>` (the old `vNNN - …` convention ended at `v0.0.349`); other commits use conventional-commit style (`feat:`, `fix:`, `chore:`…).

The `0.x` line (`0.4.0`, MUI 5 + React 18) stays published for apps that haven't migrated, critical fixes only. All stages live on a **single branch, `atualizacao-dependencias`** (not merged into `main`, nothing published) — don't create one branch per stage. The build is **`tsdown` in `unbundle` mode, ESM (`.mjs`) + CJS (`.cjs`)** (decision D1); it needs Node ≥ 22.18 to build (24 LTS in CI) — a build-time requirement only. Things from these stages that affect everyday work here:

- **MUI, Emotion, `react-hook-form`, `dayjs` and `react-toastify` are peers** — the version that actually runs is the *consumer app's*. Any MUI major bump is a coordinated, breaking release. Peers live in `peerDependencies` **and** `devDependencies` of the root `package.json` (a package missing from both used to get **bundled into `dist/` silently** — how a copy of `@mui/system` ended up there before 0.1.0; `tsdown.config.mts` now fails the build on that via `deps.onlyBundle: []` / `deps.onlyImport`). The root `dependencies` must equal `lib-package.json`'s `dependencies`.
- **Import MUI only from `@mui/material` / `@mui/icons-material` / `@mui/x-date-pickers`**, never `@mui/system` or other undeclared packages. `node scripts/check-externals.mjs` (part of `check:package`) checks every import in `dist/**` against `lib-package.json`.
- **The build can silently produce broken output:** `strict: false` + `noEmit: true` means type errors don't block, and MUI Grid v2 ignores `item`/`xs` without any error. Since `1.0.0` the lib uses Grid v2 (`size`): public `xs`/`sm`/`md` map to `size` (`true` → `'grow'`), and **a v2 item only gets its width inside a v2 `<Grid container>`** (the width is `calc()` over `--Grid-parent-columns`, set by the container) — outside one, or inside `GridLegacy`, it is full width. MUI 9 also removed system props (`<Box border=…>`, `<Typography textTransform=…>`): use `sx`. `Typography`'s `color` prop only takes palette names (`'primary'`, `'textPrimary'`); a theme path like `'text.primary'` silently renders black. Visual verification through Storybook is mandatory for layout-affecting changes.
- **Published layout: ESM in `.mjs`/`.d.mts`, CJS in `.cjs`/`.d.cts`, `"type": "commonjs"`, and `typesVersions` for the `types/*` subpaths** (node10 ignores `exports`). attw is clean in every mode with no ignored rule — keep it that way. Until `1.0.0-rc.1` the ESM had to stay in `.js`: in Next 14, webpack applies strict interop inside `.mjs`, so `import Image from 'next/image'` (CommonJS there) became the module object and SSR broke (React #130). Next 14 left the peer range in `rc.2`, and the smoke on Next 16 consumes the `.mjs`. If a future peer floor brings that back, the smoke app's `/next-apis` page is what catches it.
- **The root `package.json` must not have `"type": "module"`.** rolldown reads it for the sources and switches to Node-mode interop (`__toESM(x, 1)`), which makes every default import of a CJS module (`import Grid from '@mui/material/Grid'`) resolve to the module object in the CJS output. The smoke app consumes the ESM, so it would not catch this; `check:package` fails on any `__toESM(x, 1)` in `dist/**/*.cjs`.
- **Don't go ESM-only (evaluated in `rc.2`, kept dual).** The CJS output is what `require` gets in the apps' Jest and Node scripts; dropping it would force every app's test setup to change for no gain in Next, which consumes the `.mjs`.
- **Pickers (x-date-pickers 8+) use the accessible field DOM:** the field is a group of `role="spinbutton"` sections plus a hidden `<input>` holding the formatted value — there is no text input. Style the field through `.MuiPickersInputBase-*` / `.MuiPickersOutlinedInput-*` (the old `.MuiOutlinedInput-root` and `div input` selectors silently stop matching), and in tests use `campoDoPicker`/`digitarNoPicker` from `src/stories/interacao.ts`.
- **`Input` no longer accepts the `TextField` props MUI 9 removed** (`InputProps`, `inputProps`, `InputLabelProps`, `FormHelperTextProps`, `SelectProps`; removed in `rc.3`, apps use `slotProps`). `MaskInput`/`GenericMaskInput` must merge the incoming `slotProps` instead of replacing them. Box-like public props that apps fill with loose system props (`customTableStyle`) go through `src/components/utils/propsDeEstilo.ts`.
- **Don't add `noValidate` to the `<form>` of `FormProvider`/`GenericFormProvider`.** Apps put their own fields with native `required` inside them (copom's `PlacaInput` registers without rules and relies on it). To show the lib's own message instead of the browser's, avoid the native constraint on the lib's field (`Input type='email'` renders `type='text'` + `inputMode='email'`, UPGRADE_PLAN.md 5.21c).
- **No debug logging in the lib** (`no-console` is an ESLint error; `console.error`/`warn` allowed). The only `console.log`s are the ones an app turns on (`Stepper`'s `debugLog`, `KeycloakAuthProvider`'s `enableDebugLogs`), each with an `eslint-disable-next-line`.
- **TypeScript 6.0** since `rc.3` (7 waits for `typescript-eslint`, Etapa 9). TS 6 checks side-effect imports (`noUncheckedSideEffectImports`): `src/css.d.ts` declares `*.css`.
- **In MUI 9 an Autocomplete's `renderInput` params come in `params.slotProps`**: when you pass your own `slotProps` to the `TextField`, spread `...params.slotProps` first, or the field loses its combobox role and handlers.
- **Storybook compiles with SWC, and there is no Babel config on purpose.** `@storybook/nextjs` only switches to Babel if it finds `.babelrc` or `babel.config.js` at the root. The old `.babelrc.json` was never read, and it was removed in Etapa 5 (UPGRADE_PLAN.md 5.19). Don't add a Babel config back: it would change the compiler under every story.
- **Keep every Storybook package on the same `^` range** (`storybook`, `@storybook/*`, `eslint-plugin-storybook`). Exact pins let the addons fall behind the core once already. If `npm install` hits `ERESOLVE` on a Storybook major, uninstall the Storybook packages and install them again: npm sticks to the installed core.
- **`DatePicker`, `GenericDatePicker` and `TimePicker` register their validation inside the picker's `inputRef` callback** (`inputRef={() => { context.register(name, { validate }) }}`). It looks odd, but it is load-bearing: that is where required and min/max dates are validated. Don't drop it when migrating the pickers (Etapa 7), and never return anything from a callback ref (React 19 treats the return value as a cleanup). `src/components/form/date/pickers.test.tsx` guards it (UPGRADE_PLAN.md 5.16).
- **Parse formatted dates only through `src/components/utils/dayjs.ts`** (`import dayjs from '../../utils/dayjs'`), never straight from `'dayjs'`. It registers `customParseFormat`; without it `dayjs('15/03/2024', 'DD/MM/YYYY')` ignores the format. x-date-pickers 6 used to register the plugin as an import side effect, which hid the missing registration; 7+ registers it only when the adapter mounts, after the component already parsed, so the first picker on a page lost its `defaultValue` (UPGRADE_PLAN.md 5.17). Since Etapa 7 the devDependencies are on pickers 9 (lazy adapter), so `utils/dayjs.test.tsx` does exercise this; the smoke's `verificar-datepicker.cjs` also checks it.
- **Never touch browser APIs (`localStorage`, `window`, `document`) during render** — it breaks SSR in the consumer apps. Read them in `useEffect`, or gate the JSX with `useIsClient()` (`src/components/utils/useIsClient.ts`), as `Table`/`GenericTable` do. `Table.ssr.test.tsx` renders in a `node` environment to catch this.
- **The smoke app's `file:../../dist` link does not install the lib's own `dependencies`** (npm `install-links=false`) and resolves MUI from the repo root. `npm run smoke` does it right: packs `dist/`, installs the tarball in `examples/smoke-app` and runs `next build` (which also SSR-renders the pages). Since `rc.2` it runs once in CI, on the smoke app's own `package.json`, which is the current stack (Next 16, React 19, MUI 9, pickers 9, toastify 11) — each peer has a single major, so there is no floor/top matrix anymore. `SMOKE_NEXT`/`SMOKE_MUI`/`SMOKE_PICKERS`/`SMOKE_TOASTIFY` remain for trying a peer's next major before adopting it (`SMOKE_MUI` sets material + icons-material). Locally, if it fails with `ERESOLVE` after changing majors, delete `examples/smoke-app/node_modules` (CI always starts clean). After `next build` it runs `examples/smoke-app/verificar-datepicker.cjs`, a fresh-process SSR render of a `DatePicker` with `defaultValue`. The `/next-apis` page covers the lib's `next/*` imports (`NavBar`, `Map`).
- **`check:package` now starts with `scripts/check-externals.mjs`**: fails if the bundle (JS or `.d.ts`, recursively) imports an undeclared package, if `src/` imports a package missing from `lib-package.json`, or if a declared dependency is unused. Then `scripts/check-use-client.mjs` checks that every `'use client'` module in `src/` keeps the directive in `dist/` (`.mjs` and `.cjs`) — rolldown warns `MODULE_LEVEL_DIRECTIVE` falsely in unbundle mode and the warning is suppressed in the config.

### Agent tooling: MUI docs (MCP + llms.txt)

`.mcp.json` registers the **official MUI MCP** (`mui-mcp`, `npx -y @mui/mcp@0.1.6`, project scope; Claude Code asks to approve it on first use). It serves the official Material UI and MUI X docs **per version**: Material UI 5.18/6.5/7.3/9.4, x-date-pickers 6–9, x-charts 6–9.

- **Use it before writing or changing any MUI / MUI X usage**, not memory. Every silent regression in Etapa 7 (`Typography color='text.primary'`, Grid v2 needing a container, `*Outline` icons, pickers DOM) was a documented API change. Call `useMuiDocs` with the package, then `fetchDocs` on the links it returns.
- **Use the docs of the major in the peers** (MUI 9 / pickers 9 since `rc.2`, one major each). The MCP also serves older versions, useful to compare when a behavior changed.
- Without the MCP, the same docs are at `https://llms.mui.com/<package>/<version>/llms.txt` (`material-ui`, `x-date-pickers`, `x-charts`), migration guides included (`…/material-ui/9.4.0/migration/upgrade-to-v9.md`).
- **Reviewed on 27/09/2026:** official, from `mui/mui-x`, MIT. The logic lives in `@mui/x-agent-tools`: no filesystem writes, no child processes. `useMuiDocs`/`fetchDocs` fetch from `chat-backend.mui.com`/`llms.mui.com`, and `fetchDocs` has a URL guard (MUI hosts only). `generateReactCode` sends the prompt to MUI's backend and only works with `MUI_RECIPES_API_KEY`: **never configure that key here**. When bumping the version, re-review the package the same way and update it in `.mcp.json` **and** `llms.txt` (`check:package` fails if they differ).

`llms.txt` (repo root, **shipped in the package** next to `AGENTS.md`) is the index for agents in consumer apps: the lib's own docs plus the MUI docs at the exact versions the lib supports. `scripts/check-llms.mjs` (part of `check:package`) fails when a linked MUI version falls outside the peers, a peer major has no link, or the link for the installed major isn't the installed version. So a MUI bump in devDependencies or peers forces the links to be updated. `node scripts/check-llms.mjs --rede` also checks that every link responds.

### Agent tooling: the tsdown skill

`.claude/skills/tsdown/` is the **official** agent skill from the `rolldown/tsdown` repo (installed 23/09/2026 with `npx skills add rolldown/tsdown --skill tsdown -a claude-code -y`, project scope, pinned by hash in `skills-lock.json`). It is project tooling for agents, **not** a requirement for people: build correctness is guaranteed by `check:package`, the public-API diff, `npm run smoke` and the snapshots, whoever writes the config.

- **Use it whenever you touch the build** (`tsdown.config.*`, `exports`, `.d.ts`, externals). tsdown is pre-1.0 and v0.23 **silently ignores removed options** — wrong output, no error. Check every option against `references/option-*.md` instead of relying on memory (e.g. externals are `deps.neverBundle` in 0.23, not `external`).
- **Keep it in sync with the installed tsdown.** When bumping tsdown, run `npx skills update tsdown` (project scope — never `-g`) and review the diff in the PR. The skill says which tsdown version its docs were generated from; a skill older than the installed tsdown is the problem it exists to prevent.
- **Review it like code.** It is third-party instruction text that runs with the agent's permissions. The installed copy was reviewed on 23/09/2026: Markdown only, no scripts, byte-identical to `rolldown/tsdown@eb40c95`. The `skills` CLI's own scan labelled it "Critical Risk" without detail (Socket: 0 alerts, Snyk: low); the only candidates found are doc examples with `execSync('rm -rf dist')` and a release script that runs `execSync('npm publish')`.
- **Never follow that `npm publish` example here.** This repo publishes only through the `v*` tag workflow (`.github/workflows/publish.yaml`); no script or agent runs `npm publish`.
- Only the `tsdown` skill is installed. The repo's other skill, `tsdown-migrate`, is for migrating from `tsup` — we come from microbundle, so it doesn't apply.

### Agent tooling: the `atualizar-ssplib` skill (for the consumer apps)

`skills/atualizar-ssplib/` is **our own** skill, written for the apps, not for this repo (so it lives in `skills/`, the `skills` CLI layout, not in `.claude/skills/`). Apps install it with `npx skills add SSPDF/ssp-components --skill atualizar-ssplib -a claude-code` (or a local path). It walks an agent through updating the lib in an app: `scripts/diagnostico.mjs` (zero deps, read-only) compares the app with a target version or `.tgz`, prints the install commands and flags the code patterns the MUI codemods miss; `references/0.x-para-1.x.md` has the codemod order and the manual fixes. Validated on the specto and the viva-flor (30/09/2026).

- **When a release changes what apps must do, update the skill in the same change**: a new category in the script's `EXPLICACAO` + scanner, or a new `references/<de>-para-<para>.md`. The CHANGELOG's "O que o app precisa fazer" stays the source; the skill makes it executable.
- **Every problem found while migrating an app is fixed here first** (lib or skill), then the migration goes on. Test scanner changes against a small synthetic app (a `pages/*.tsx` with the pattern, `node_modules` symlinked from a real app) before re-running on an app.
- The install sequence matters: everything that changes major is uninstalled **first** (the lib and the app's own deps being bumped), or npm checks the new peers against old transitive deps still in the lock and fails with `ERESOLVE` blaming the new lib itself (specto: the old lib's `react-leaflet` 4; viva-flor: `x-charts` 6's `@react-spring`).
- `skills/*/scripts/**` are CLIs: `no-console` is off there, as in `scripts/**`.
- **Apps must list the lib in `transpilePackages`** (since `rc.2`, ESM in `.mjs`). Without it Next loads the lib as a native Node ESM external in SSR: subpaths like `dayjs/plugin/customParseFormat` and `next/image` don't resolve / come as the module object, and `next build` fails. Decided 30/09/2026 (viva-flor): **the fix goes in the app, not the lib** — don't add `.js` extensions or interop shims to the lib to support non-transpiling apps. The smoke-app transpiles, like the apps must. The skill flags a missing entry (`transpile`).
- **Local copies of lib components in an app** (`copia-da-lib`): the skill tries to replace them with the lib's component first, after a contract check (form context, stored value format, initial value from `reset`, `unregister` on unmount, props, visuals), and only fixes the copy when the contract differs. Unused copies are deleted. Decided 30/09/2026.
- **Never regress the lib to fit an app** (wider peer range, compatibility shim, old API back): the app updates. Only a real lib bug is fixed in the lib, and only after asking.

### Verification (added in Etapa 0 — there used to be none)

```bash
npm run typecheck    # tsc --noEmit
npm run lint         # eslint 10 flat config (0 errors; warnings are tracked debt — incl. the React Compiler rules of react-hooks 7, downgraded to warn)
npm run format:check # prettier, per .prettierrc
npm run test         # vitest — auth providers, cookie helper, AutoComplete, masked GenericInput, picker validation and range message, tables (incl. SSR in a node env)
npm run snapshots    # visual snapshots of every story + every play function, inside a fixed Linux container (rebuilds Storybook first; SKIP_STORYBOOK_BUILD=1 to skip; SNAPSHOTS_DETALHE=1 also lists and saves sub-threshold diffs)
npm run e2e:keycloak # real keycloak-js in the browser against scripts/lib/oidc-simulado.mjs (no Docker); E2E_KC_* targets a real Keycloak (HMG)
npm run interacoes   # only the interaction stories (tag `interacao`), against a running `npm run storybook` — fast local loop (`-- --url`, `-- --filtro`)
```

**Vitest 5: a `vi.fn` with an arrow-function implementation can't be called with `new`** — mock constructors with `vi.fn(function () { return obj })` (see `KeycloakAuthProvider.test.tsx`).

**Each story is captured in a fresh browser context** (`scripts/visual-snapshots.mjs`): with one shared page, some stories rendered differently depending on the stories before them, and the old baseline recorded that (UPGRADE_PLAN.md 5.18). Keep the isolation.

**Snapshots must be generated inside the container** (`npm run snapshots:update`), never straight from macOS — fonts and antialiasing differ from CI and every PNG would show a diff. The baseline lives in `snapshots/baseline/` and is versioned.

When you change a component, update/add its story and run `npm run snapshots`. A layout regression shows up there and nowhere else.

**The Keycloak e2e is the only test that runs the real `keycloak-js`** — `KeycloakAuthProvider.test.tsx` mocks the module, so it can't catch a `keycloak-js` upgrade breaking. `npm run e2e:keycloak` builds the smoke-app (with `basePath`, like every app) and logs in through `examples/smoke-app/pages/auth-keycloak*.tsx` against a mock OIDC server that is strict where upgrades break silently (PKCE, `redirect_uri`, `nonce`, `id_token_hint`). It covers check-sso, silent SSO on reload, auto refresh, refused refresh, session ended elsewhere, logout and the `govbr` federated logout. Run it (and `SMOKE_KEYCLOAK_JS=<old> npm run e2e:keycloak` to compare) whenever you touch the provider or bump `keycloak-js`. Don't replace it with a Keycloak in Docker (~1 GB of memory, rejected). `keycloak-js` 26 is ESM-only and needs a secure context (UPGRADE_PLAN.md 5.22). The HMG variant (`.github/workflows/e2e-keycloak-hmg.yaml`, on push and on demand) uses a dedicated test client and test user created in HMG only for it; every value (URL, realm, client, role, user, password), even non-sensitive ones, lives in repo secrets (`E2E_KC_*`) by decision — the repo is public, so never move any to variables, hardcode them or write them in docs. Never point it at another app's client. GitHub masks every occurrence of a secret's value in logs, so pick values that don't show up in other text (a role named `E2E` masked every step name; the realm `ssp` still masks every "ssp").

**Interaction stories (tag `interacao`) are the behavior check** — snapshots only see the initial render, which is how four broken autocompletes went unnoticed (UPGRADE_PLAN.md, Etapa 5). Each one has a `play` function (`storybook/test`) that uses the component like a person would and asserts the result, usually what reached `onSubmit` (the form decorators render it as `data-testid='dados-enviados'`/`'arquivos-enviados'`). Helpers are in `src/stories/interacao.ts`. When you change a component's behavior, add or update its `Interacao*` story. Things that bite:
- `tags` must be a string literal (`tags: ['interacao']`); Storybook's indexer reads the file statically and fails the whole index otherwise.
- Poppers, Autocomplete lists, menus, modals and toasts render in `document.body`, outside the canvas — query them with `pagina(canvasElement)`.
- Query fields by role and accessible name (`getByRole('textbox', { name: title })`, `'combobox'`, `'group'` for pickers, `'radiogroup'`/`'radio'`). Since `rc.3` every field's label is wired to it (`useId` + `htmlFor`, or `aria-labelledby` on the picker's section group) and `Radio` follows the ARIA radiogroup pattern; `src/stories/NomesAcessiveis.stories.tsx` guards it. When you add a field component, wire its label the same way.
- Use `selecionarArquivos` for file inputs, not `userEvent.upload`: it builds a real `FileList`, which is what the browser gives the app (`FileUpload` iterates with `Array.from` since `rc.3`, so the fake one no longer breaks it, but the real one is the faithful test). Mock upload APIs in the story's `beforeEach` (return a cleanup).
- Interaction stories produce no PNG; `visual-snapshots.mjs` waits for the render phase `finished` and fails on a play error (`scripts/lib/storybook-play.mjs`).

**Error states are snapshotted too** (`src/stories/EstadosDeErro.stories.tsx`, tag `erro-visual`): each required field after an empty submit (its `play` runs before the PNG; the runner hides the toast). Add a story there when a field gets new error styling.

**The 0.1% snapshot tolerance hides small real regressions** (in Etapa 7 it hid `Typography color='text.primary'` turning black). When reviewing a migration or a dependency bump, run `SNAPSHOTS_DETALHE=1 npm run snapshots`: it lists every story with any changed pixel and saves the images to `snapshots/__diff__/`.
